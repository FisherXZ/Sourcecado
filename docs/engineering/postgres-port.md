# Postgres port: rules for store slices

This guide is for the slices that move one store from SQLite to Postgres (S02,
S04, S06, S07, S08). It applies until slice S15 replaces the phase 1 seam.
The plan and the slices are in `docs/superpowers/plans/2026-11-09-hosted-migration-*`.

Several store slices run at the same time. These rules keep them from
colliding.

## The seam

A store keeps its constructor. It still takes the state directory.

```python
from coworker import db

class PersonStore:
    def __init__(self, base_dir):
        self.base = Path(base_dir).expanduser()
        self._db, self._user_id = db.resolve(self.base)

    def get(self, person_id):
        with self._db.tx(self._user_id) as conn:
            return conn.execute(
                "select ... from people where user_id = %s and id = %s",
                (self._user_id, person_id),
            ).fetchone()
```

- Call `db.resolve()` in the constructor only, never in a worker thread.
- `Database.tx(user_id)` is one transaction. It commits when the block ends and
  rolls back when the block raises. A write that must be atomic across several
  statements stays inside one `tx` block. Pass the connection to helpers; do not
  open a second `tx` for the same unit of work.
- Do not keep a connection on `self`. Do not cache rows on `self`.
- The service resolves every directory to one database and the development user
  (`DEV_USER_ID`). Tests and evals resolve each directory to its own new user.
  So `PersonStore(tmp_path / "a")` and `PersonStore(tmp_path / "b")` stay
  isolated, and a store that is opened again at the same directory sees its
  rows. Most tests need no change for this.
- Do not write SQL that joins the tables of two stores. In a test, two stores of
  one app can sit at two directories, which are two users.

## Tables

- One migration file for each slice: `supabase/migrations/<timestamp>_<store>.sql`.
  Use the timestamp that your slice was given. Do not edit another slice's file.
- Write the head schema. Do not replay the SQLite migration history.
- Every table: `user_id uuid not null references auth.users(id) on delete cascade`,
  and an index that starts with `user_id`.
- Add `user_id` to each unique key that is unique for one user.
- Keep column types close to SQLite: `TEXT` stays `text`, `INTEGER` becomes
  `bigint`, an autoincrement key becomes
  `bigint generated by default as identity`. No type upgrades in these slices.
- Every query filters by `user_id`. Row-level security arrives in S18 as a
  second barrier; it does not replace the filter.

## SQL translation

| SQLite | Postgres |
| --- | --- |
| `?` | `%s` |
| `BEGIN IMMEDIATE` | One `tx` block, plus `select ... for update` on the contended row, or `pg_advisory_xact_lock`. Decide for each site and say why in the PR. |
| `INSERT OR REPLACE` | `insert ... on conflict (...) do update` |
| `INSERT OR IGNORE` | `insert ... on conflict do nothing` |
| `cursor.lastrowid` | `returning id` |
| `sqlite3.Row` | `conn.cursor(row_factory=psycopg.rows.dict_row)` |
| `PRAGMA user_version`, `PRAGMA table_info` | Removed. The migration file defines the schema. |
| `executescript` | Separate statements in one `tx` block |

## Shared files

More than one slice changes these files. Keep each change small and local, so
that the merges are easy.

- `backend/coworker/migrations.py` and `backend/coworker/doctor.py`: remove only
  the entries and checks for your store. Delete the doctor and migration tests
  that cover only your store.
- `backend/coworker/server.py`: change only the lines that construct or use your
  store.
- `backend/tests/state_fixtures.py` and other shared fixtures: change only what
  your store needs.
- Do not change `backend/coworker/db.py`, `backend/coworker/pg_scratch.py`, or
  `backend/tests/pg_fixtures.py`. If the seam does not fit, stop and report.

## Tests

- Start the database with `make db-up`. Tests and evals create and drop their own
  scratch database.
- The fixtures empty every table after each test and reset identity counters.
- Identity counters are shared by all users. In a test with two stores, the
  second store's first row can get id 2. Change the test to read the id that the
  store returns.
- A verify step must fail when the task is done wrong. For each new test of
  isolation or locking, break the code on purpose one time and see the test fail.
  Record that in the PR.
- The slice is not done until these pass:
  - `cd backend && .venv/bin/pytest -q`
  - `cd backend && .venv/bin/python -m coworker.evals --suite sourcing --artifacts .eval-artifacts`
  - the module has no `sqlite3` import

## QA

Run the standard smoke in the slices document with the mock provider, on
`http://127.0.0.1:5180`. Start the backend with `make backend`, which sets
`DATABASE_URL` to the local database. Run `make db-reset` first; it applies the
migrations and seeds the development user.
